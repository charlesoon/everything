1. 현재 경로 (비관리자 = MFT 실패 → WalkDir 폴백)

관리자 권한이 없으면 \\.\C: raw 볼륨 접근이 막혀 MFT 스캔이 실패하고 run_nonadmin_index로 폴백합니다 win/mod.rs:165. 흐름:

Phase 1 홈 얕은 스캔 (depth≤6) ─→ early MemIndex(≤200k) ─→ 검색 가능 Phase 2 홈 깊은 스캔 ∥ C:\ 나머지 루트 스캔 (★ 두 스캔 동시 실행) └─→ 전체 MemIndex(all_entries) 빌드 ─→ 상태 "Ready" Phase 3 (백그라운드) DB bulk upsert ─→ 인덱스 4개 생성 ─→ ANALYZE ─→ MemIndex 해제 ─→ RDCW watcher

2. 목표 1 — 인덱싱 2배 가속

D1 · 최대 효과 stat + 엔트리 생성을 병렬 풀로 이동

현재 scan_dir_jwalk는 walk만 병렬이고 처리는 직렬(B1). main.rs의 fresh 병렬 인덱서와 동일하게, jwalk::WalkDirGeneric의 process_read_dir 콜백(=워커 스레드) 안에서 symlink_metadata를 호출하고 CompactEntry까지 만들어 bounded 채널로 단일 수집 스레드에 배치 전송합니다. 수집 스레드는 all_entries에 넣기만 합니다.

효과: 수백만 건의 stat + String 할당이 N개 코어에 분산. 멀티코어에서 이 단계가 지배적이므로 2배 이상 기대. main.rs에 검증된 패턴이라 일관성도 확보. 참조: main.rs:3100-3262 fresh 병렬 스캔

D2 단일 공유 rayon 풀 (풀 2개 → 1개)

deep 스캔과 roots 스캔이 각자 풀을 만드는 대신(B2), main.rs의 build_scan_pool()처럼 하나의 공유 풀을 만들어 모든 루트를 RayonExistingPool로 처리. 루트별 풀 생성/해제 비용 제거 + 스레드 수를 한 번에 통제(→ 목표 2와 직결).

D3 여분 stat 제거 (Windows는 열람 시 메타데이터 무료)

Windows FindNextFileW는 디렉터리 열람 때 크기·시간·속성을 함께 돌려줍니다. D1에서 process_read_dir 한 곳에서만 stat하면 소비자 쪽의 별도 entry.metadata()(:547)가 사라져 엔트리당 syscall 1회로 축소됩니다.

D4 · 선택 DB 삽입을 스캔과 파이프라인

"인덱싱 시간"에 DB 영속화까지 포함된다면(현재 indexing_active는 Phase 3 종료까지 true), 스캔 배치를 채널로 받아 스캔 중에 DB upsert를 병행. 단 MemIndex는 전체 엔트리가 필요하므로, D1의 수집 스레드가 (a) all_entries 적재와 (b) DB writer로의 배치 전달을 동시에 하도록 확장. 벽시계 시간 = max(스캔, DB삽입)으로 단축. 주의: DB writer는 반드시 1스레드(SQLite 단일 writer).

3. 목표 2 — CPU 포화로 인한 UI 블록 제거

run_nonadmin_index는 백그라운드 스레드에서 돌지만(win/mod.rs의 spawn), 문제는 스캔 워커들이 모든 코어를 최우선으로 점유해 Tauri webview의 렌더/입력 스레드가 스케줄되지 못하는 것입니다. 두 축으로 해결:

C1 병렬도에 UI 여유분 남기기

D2의 단일 풀 크기를 전체 코어가 아니라 max(2, n_cpus − 2)로 제한. 현재 최대 16 워커(B2)가 문제이므로, 8코어 기준 6 워커로 캡 → 최소 1~2 코어가 항상 UI/OS용으로 남습니다. 스캔은 I/O 바운드라 코어를 다 쓰지 않아도 속도 손실이 작습니다.

C2 · 핵심 스캔 워커 스레드 우선순위를 BELOW_NORMAL로

rayon ThreadPoolBuilder::start_handler에서 각 워커 스레드에 SetThreadPriority(THREAD_PRIORITY_BELOW_NORMAL)를 설정. OS 스케줄러가 UI 스레드(NORMAL)를 스캔 워커보다 먼저 실행 → CPU가 바빠도 UI는 즉시 반응. 스캔은 UI가 유휴일 때 남는 사이클을 채워 총 시간 손실은 미미.

하지 말 것: 프로세스 전체 background 모드(PROCESS_MODE_BACKGROUND_BEGIN)는 I/O 우선순위까지 낮춰 인덱싱을 느리게 만들어 목표 1과 충돌합니다. 스레드별 CPU 우선순위만 낮춥니다.

C3 풀 스래싱 제거 (부수 효과)

C1의 단일 풀은 루트마다 풀을 만들고 버리던 스파이크(B2)를 없애 CPU 사용을 균일하게 만듭니다. 진행률 emit은 이미 200ms로 스로틀됨 :19,:596 — 유지.

4. 부수 목표 — 메모리 (~1300MB 완화)

M1 · 최대 효과 per-scan Vec 동시 생존 제거

D1의 채널 수집으로 자연 해결(B3): 각 워커 배치를 즉시 하나의 all_entries로 흘려보내면 루트별 결과 Vec을 동시에 들고 있을 필요가 없어져 병합 시 ~2배 피크가 사라집니다.

M2 초기 용량 과다 예약 제거

Vec::with_capacity(2_000_000)(B5, 224MB)를 제거하거나 실측 기반 추정으로 축소. 자연 증가에 맡기거나 홈 얕은 스캔 결과로 총량을 추정.

M3 · 선택(큰 변경) 디렉터리 문자열 인터닝

가장 큰 낭비인 CompactEntry.dir 중복(B4)을 dir → Arc<str> 또는 dir-id 테이블로 인터닝하면 엔트리당 힙을 크게 줄일 수 있습니다(같은 폴더 파일이 포인터/id만 공유). 단 mem_search의 dir_map·검색 경로·path() 재구성에 영향 → 별도 단계로 신중히. 우선순위 낮음.

권장 단계

  1. 1단계 (핵심, 즉효): D2 + C1 + C2 — 단일 풀 + 코어 캡 + 워커 우선순위. 작은 변경으로 목표 2(UI 블록)를 먼저 해결하고 CPU 스파이크 완화.
  2. 2단계 (2배 가속): D1(+D3, +M1) — stat/생성 병렬화 + 채널 수집. 목표 1 달성의 핵심.
  3. 3단계 (마감): M2, 그리고 필요 시 D4(파이프라인)·M3(인터닝).

6. 검증 방법

  • 속도: 기존 [nonadmin +Xs] stderr 타임스탬프로 Ready 도달 시간과 Phase 3 완료 시간을 각각 before/after 측정. 목표 총 ≤ 75s.
  • 메모리: 작업 관리자/PowerShell Get-Process peak working set을 before/after. 목표 피크 대폭↓.
  • CPU/UI: 인덱싱 중 CPU% 및 UI 체감(검색 입력 지연, 스크롤) 관찰. C2 적용 후 CPU가 높아도 입력이 즉시 반응하는지 확인.
  • 정확성: 인덱싱 후 엔트리 수·검색 결과가 기존과 동일한지( cargo test 회귀 + 수동 검색 스팟체크).
