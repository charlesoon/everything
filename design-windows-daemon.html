설계 대비 변경 1건 메인 수신 루프: break → drain-and-skip

승인된 설계는 "메인 수신 루프도 배치마다 취소 확인"이었으나, 워커가 아직 전송 중일 때 메인이 먼저 break하면 bounded sync_channel 송신이 영구 블록 → thread::scope join 데드락이 발생합니다. 따라서 메인 루프는 취소 시 수신은 계속하되(채널을 비워 워커 송신 블록 방지) 쓰기만 건너뛰도록 구현했습니다. 워커는 break 'roots로 즉시 멈춰 채널을 닫으므로 메인 루프도 곧 종료됩니다. 취소 후 추가 작업량은 (워커의 다음 4096-체크까지 + 버퍼된 배치)로 유계이며, 취소 인지 후 DB 쓰기는 0입니다.

필요 추가 1건 RDCW apply_changes의 indexing_active 게이트

reconcile가 watcher 상주 중 build_index를 돌리므로, watcher가 indexing_active 동안 서지 않으면 daemon 내부 dual-writer가 됩니다. macOS watcher가 이미 따르는 불변식(main.rs:3826, "All three already stand down on indexing_active")을 RDCW에도 적용했습니다. 이벤트는 큐에 남겨 패스 종료 후 반영 → 유실 없음. GUI 재인덱스 시에도 동일하게 올바른 동작(회귀 아님).

2. 문제점 (심각도 순)

P1 · Critical 인덱싱 패스 중 GUI 등장 → dual-writer 창

build_index(= run_incremental_index)에는 중단 지점이 전혀 없습니다. daemon은 패스와 패스 사이에서만 gui.lock을 확인합니다 daemon.rs:396-405. C:\ fresh 빌드는 수 분~수십 분 걸리는데, GUI의 wait_for_daemon_exit는 10초 후 포기하고 쓰기를 시작합니다 daemon.rs:50, main.rs:7182.

결과: WAL writer 2개 경합(SQLITE_BUSY), 그리고 로직 레이스 — 예: GUI가 인계받은 뒤 daemon이 뒤늦게 index_complete=1·last_run_id를 써서 GUI가 방금 만든 상태를 오염시킬 수 있음. "GUI 실행 → daemon 자연 종료" 요구사항의 실질적 구멍.

P2 · High 60초 주기 C:\ 전체 재스캔 — 상시 디스크/CPU 부하

last_catchup이 패스 시작 시점에 리셋되므로 daemon.rs:401-403, 패스가 60초를 넘기면(전체 드라이브 walk이므로 일반적) 쉬는 시간 없이 연속 재스캔이 됩니다. 노트북에서는 배터리·발열 문제로 직결됩니다.

P3 · High 실시간 감시 부재 — 변경 반영 지연 = 재스캔 주기

daemon 주석 그대로 "no headless live watcher yet" daemon.rs:390. 파일 변경이 다음 재스캔까지(최대 수 분) MCP 검색에 반영되지 않습니다. macOS daemon(FSEvents 실시간)과의 결정적 격차.

P4 · Medium RDCW watcher가 AppHandle에 결합 — headless 호출 불가

rdcw_watcher::start_with_roots(app: AppHandle, …) rdcw_watcher.rs:40-44. daemon에는 Tauri 런타임이 없으므로 현재 시그니처로는 호출할 수 없습니다. (내부 사용은 emit 2곳뿐이라 분리 비용은 낮음 — §1 참조.)

P5 · Medium Windows용 yield_to_gui 부재

watcher를 세우고 종료를 기다린 뒤 daemon.lock을 놓는 yield_to_gui는 macOS 전용입니다 daemon.rs:321-329. daemon에 RDCW를 붙이면 Windows에도 같은 절차가 필요합니다 — 없으면 watcher의 마지막 flush와 GUI의 첫 쓰기가 겹치는 짧은 dual-writer 창이 생깁니다.

P6 · Low RDCW 이벤트 유실이 조용히 무시됨

event_loop이 Err 이벤트(버퍼 오버플로 등)를 버립니다 — if let Ok(ev) = result rdcw_watcher.rs:107. 대량 변경 시 유실분이 다음 재조정(reconcile)까지 누락됩니다.

P7 · Low GUI 종료 후 daemon 재상주 없음

GUI가 꺼지면 gui.lock은 풀리지만 아무도 daemon을 다시 띄우지 않습니다. 다음 MCP 세션이 시작될 때까지 인덱스가 정체됩니다. (macOS도 동일한 한계.)

3. 설계

전체 그림

┌─ everything --mcp (read-only) ─────────────────────────────────┐ │ query_only=ON 검색만 수행 · 시작 시 spawn_detached() (기존 그대로) │ └────────────────────────────────────────────────────────────────┘ │ spawn (GUI/daemon 부재 시에만) ▼ ┌─ everything --daemon (비관리자 writer) ── Phase A/B에서 신설·보강 ─┐ │ 1. daemon.lock 획득, gui.lock 확인 (기존) │ │ 2. build_index: fresh 빌드 or catchup (기존 + 취소 가능화) │ │ 3. RDCW watcher 상주: 실시간 upsert/delete (신설: headless화) │ │ 4. supervise: 빌드 힐링 + watcher 재시작 (신설: macOS와 대칭) │ │ 5. reconcile: 1시간 주기 or RDCW 유실 시 catchup (신설) │ │ 6. gui.lock 감지(300ms) → 취소+yield → 종료 (기존 + P1/P5 보강) │ └────────────────────────────────────────────────────────────────┘ │ gui.lock 감지 → 1~2초 내 종료 ▼ ┌─ Everything GUI (writer 인계) ─────────────────────────────────┐ │ hold_gui_beacon → wait_for_daemon_exit(≤10s, 이제 항상 성공) │ │ → 기존 Windows 체인: MFT→USN(관리자) / WalkDir→RDCW(비관리자) │ │ 종료 시 spawn_detached() → daemon 재상주 (Phase C, 선택) │ └────────────────────────────────────────────────────────────────┘

Phase A — daemon을 이벤트 기반 writer로 (P2·P3·P4·P5·P6 해결)

  1. rdcw_watcher headless화: start/start_with_roots의 app: AppHandle → Option<AppHandle>. pathignore_changed emit은 Some일 때만; refresh_and_emit_status_counts는 이미 Option을 받으므로 그대로 통과. GUI 호출부는 Some(app)으로 무변경 동작.
  2. daemon.rs에 run_windows_resident 신설 (Windows에서 run_polling_resident 대체, 타 OS는 폴링 유지):
    • 시작: build_index(기존) → compute_watch_roots(&state)로 RDCW 시작
    • 루프: 300ms gui.lock 폴 + 5초 supervise(index_complete 힐링, watcher_active 죽으면 재시작) — run_macos_resident와 대칭 구조 daemon.rs:337-363 미러링
    • reconcile: 기본 1시간 주기로 catchup 패스 1회(변경분만 upsert하는 SubtreeDiff 방식이라 I/O 위주) — RDCW 유실 보정망
  3. RDCW 유실 감지: event_loop이 Err 이벤트 수신 시 플래그를 올리고, daemon supervise가 이를 보면 reconcile을 즉시 트리거 (P6).
  4. yield_to_gui 공용화: #[cfg(macos)] 제거 — GUI 감지 시 watcher_stop set → watcher_active=false 대기(≤3s) → return(daemon.lock 해제). RDCW 루프는 1초 주기로 stop 플래그를 확인하므로 rdcw_watcher.rs:92-101 3초 데드라인 내 정상 종료.

Phase B — 인덱싱 패스 협조적 취소 (P1 해결 — 핵심)

  1. AppState.cancel_index: Arc<AtomicBool> 추가 (기본 false, GUI 경로는 사용하지 않음 — GUI는 writer 소유자라 취소 불필요).
  2. 취소 체크 지점 3곳 (run_incremental_index_inner):
    • fresh 워커 walk 루프 — 4,096엔트리마다 확인, set 시 walk 중단
    • catchup 워커 walk 루프 — 동일. 미완주 root의 삭제 목록은 전송하지 않음 — 현재도 삭제는 root 완주 후에만 전송되는 구조라 main.rs:3298-3460 자연히 취소-안전
    • 메인 스레드 배치 수신 루프 — 배치마다 확인
  3. 취소 시 결과: Err("yielded to GUI") 반환 → index_complete=1·finalize·VACUUM 전부 미실행 (현재도 Ok일 때만 실행되는 구조 main.rs:2769-2771 그대로 활용). 이미 커밋된 upsert는 유효한 부분 진행분으로 남고, GUI 인계 후 GUI의 인덱서가 이어서 완성.
  4. daemon 측 감시: build_index 패스 동안 300ms 주기로 gui_is_running을 폴링하는 경량 감시 스레드를 두고, 감지 시 cancel_index set → 패스가 1~2초 내 중단.
  5. 효과: daemon이 어느 단계(fresh 빌드/catchup/watcher 상주)에 있든 GUI 등장 후 1~2초 내 쓰기 중단·종료 → wait_for_daemon_exit(10초)가 항상 성공 → dual-writer 창 제거.

Phase C — 상주 수명 보완 (P7 해결 — 선택, 추천)

  • GUI 종료 시(Tauri RunEvent::Exit) spawn_detached() 호출 → GUI를 닫아도 daemon이 이어받아 인덱스가 계속 신선. 관리자 권한·installer 변경 불필요, macOS에도 동일 이득. (원치 않으면 제외 가능 — 이 경우 다음 MCP 세션 시작 때 daemon이 재기동되는 현행 유지.)

4. 동작 시나리오 (설계 적용 후)

  1. 에이전트가 --mcp 실행 → daemon 부재 시 spawn → daemon이 비관리자로 fresh 빌드(또는 catchup) 시작. MCP는 index_complete=1 전까지 "준비 중" 응답 mcp_server.rs:135-158, 이후 즉시 검색.
  2. 상주: RDCW가 실시간 upsert/delete(반영 ~1-2초), 1시간마다(또는 유실 감지 시) catchup reconcile. 재스캔 폴링 없음 → 유휴 시 CPU ≈ 0%.
  3. GUI 실행: beacon 감지(≤300ms) → 진행 중 패스 취소(≤2초) → watcher 정지 → daemon.lock 해제·종료 → GUI가 대기 통과 후 기존 Windows writer 체인 가동. 사용자 체감: GUI 시작이 기다림 없이 진행.
  4. GUI 종료 (Phase C): spawn_detached() → daemon이 catchup으로 GUI 사용 중 변경분 흡수 후 재상주.

5. 리스크 / 트레이드오프

  • RDCW의 커버리지 한계: 버퍼 오버플로·감시 실패 root의 이벤트는 유실될 수 있음 → 1시간 reconcile + 유실 즉시 트리거로 보정. 비관리자 제약상 USN 수준의 무결성은 불가(원조 Everything도 동일한 한계).
  • ACL 보호 디렉터리 미인덱스: 비관리자 daemon은 접근 불가 경로를 스캔하지 못함 — 기존 비관리자 GUI와 동일 수준이며, 관리자 GUI가 만들어 둔 행은 권한-안전 삭제 로직이 보존(§1).
