Everything v0.5.0 코드 기준 (2026-07-21) — daemon.rs, mcp_server.rs, main.rs, win/mod.rs, tauri.conf.json 검토 결과

Q1. Windows에서 --mcp(headless)로 돌리면 mac처럼 --daemon writer 프로세스를 spawn하나?

예, spawn은 됩니다. spawn 로직은 플랫폼 공통이고 Windows 전용 detach 플래그까지 구현돼 있습니다. 다만 spawn된 daemon의 내부 동작은 mac과 크게 다릅니다 — Windows에서는 실시간 watcher도, MFT/USN도 쓰지 않고 60초 주기 C:\ 전체 재스캔(jwalk)만 돕니다.

Spawn 경로 (플랫폼 공통)

  • run_stdio_server()가 시작 시 무조건 daemon::spawn_detached()를 호출합니다. 플랫폼 분기 없음. mcp_server.rs:452
  • spawn_detached()에는 Windows 전용 detach 처리가 명시적으로 들어있습니다: DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW creation flags — MCP 세션이 죽어도 daemon이 살아남고 콘솔 창도 뜨지 않습니다. daemon.rs:251-258
  • 가드 2개도 Windows에서 동일하게 동작합니다 (fs2 advisory lock = Windows LockFileEx):
    • GUI 실행 중(gui.lock 보유) → spawn 안 함 daemon.rs:225
    • daemon 이미 상주(daemon.lock) → spawn 안 함 daemon.rs:229

실무적 함의

  • C:\ 전체 jwalk을 60초마다 반복: last_catchup이 패스 시작 시점에 리셋되므로 daemon.rs:401-403, 한 패스가 60초를 넘기면(C:\ 전체 walk이라 흔함) 사실상 쉼 없이 연속 재스캔 → 상시 디스크/CPU 부하 우려.
  • daemon은 MCP를 띄운 사용자의 일반 권한으로 돌기 때문에 ACL 보호 디렉터리는 permission error로 건너뜁니다 (GUI의 nonadmin_indexer 같은 home-dir 우선 최적화도 없음).
  • GUI가 뜨면 handshake는 mac과 동일하게 동작: daemon이 gui.lock을 300ms 주기로 감지해 자진 종료 daemon.rs:397-399, GUI는 wait_for_daemon_exit(최대 10초)로 대기 후 쓰기 시작 main.rs:7182.

Q2. installer를 background(silent)로 설치할 때 --daemon을 서비스로 등록할 수 있나? 관리자 권한이 필요한가?

진짜 Windows 서비스(SCM) 등록은 가능하지만 (1) 설치 시 관리자 권한 필수, (2) 현재 --daemon은 SCM 프로토콜을 구현하지 않아 코드 수정 필요. 관리자 권한 없이 가려면 HKCU Run 키(로그온 자동 시작)가 현재 코드를 그대로 쓸 수 있는 최소 변경 대안입니다.

현재 상태

  • tauri.conf.json의 NSIS 설정에는 서비스/자동시작 관련 항목이 전혀 없습니다 (언어/아이콘만) tauri.conf.json:55-64.
  • Tauri NSIS의 installMode 기본값은 currentUser → 현재 인스톨러는 UAC 없이 per-user 설치되고, silent 설치는 installer.exe /S로 이미 가능합니다.

선택지 비교

방식관리자 권한코드 변경비고

SYSTEM 서비스로 갈 때 추가로 풀어야 할 문제

  1. DB 경로: default_db_path()는 %APPDATA% 기준입니다 mcp_server.rs:89-95. LocalSystem에서는 이것이 C:\Windows\System32\config\systemprofile\AppData\Roaming으로 풀려 사용자 DB와 다른 위치에 씁니다. 서비스 인자나 EVERYTHING_MCP_DB로 경로를 명시하거나, DB를 %ProgramData%로 옮겨야 합니다.
  2. 사용자 설정 파일: .pathignore/.pathindexing도 사용자 app-data에 있어서 서비스가 어느 사용자의 설정을 읽을지 정해야 합니다.
  3. daemon의 Windows 경로 미배선: 관리자 서비스의 실익은 MFT 전체 스캔 + USN journal(둘 다 raw volume handle \\.\C:가 필요해 사실상 관리자/SYSTEM 전용)인데, Q1에서 본 대로 현재 daemon은 이 경로를 아예 쓰지 않습니다. 서비스화 이전에 daemon에 MFT/USN을 배선하는 작업이 선행되어야 서비스가 의미를 갖습니다.

Q3. 관리자 권한으로 서비스를 등록한 뒤 GUI 앱과 MCP는 read-only로 동작하게 하면 어떨까?

방향은 좋습니다 — 현 아키텍처의 자연스러운 종착점입니다. MCP는 이미 pure reader이고(PRAGMA query_only=ON mcp_server.rs:120), "daemon이 writer 소유권을 갖는" 구조(lock handshake)도 이미 절반쯤 와 있습니다. 다만 GUI까지 reader로 만들려면 아래 5가지 설계 문제를 먼저 풀어야 하며, 중간 단계로 하이브리드(서비스가 살아있으면 GUI는 reader, 없으면 지금처럼 writer)를 권합니다.

장점

  • Single-writer가 구조적으로 보장: 지금은 gui.lock/daemon.lock advisory lock + 300ms 폴링 + 10초 bounded wait로 dual-writer window를 "줄이는" 방식인데, writer가 서비스 하나로 고정되면 이 handshake 복잡도와 WAL busy 시나리오가 통째로 사라집니다.
  • MFT+USN 상시 가동: SYSTEM 서비스는 항상 raw volume 접근이 되므로, 사용자가 GUI를 관리자로 띄우는지와 무관하게 항상 최고 속도 인덱싱·실시간 USN 감시가 가능합니다. GUI의 4단계 폴백 체인(MFT→USN→WalkDir→RDCW)이 서비스 쪽 단일 경로로 단순화됩니다.
  • GUI 기동 즉시 검색 가능: 인덱싱 부트스트랩·MemIndex 빌드가 GUI 기동 경로에서 빠집니다.

풀어야 할 문제

  1. DB 위치와 ACL: SYSTEM이 쓰는 DB를 사용자 프로세스가 읽어야 하므로 %ProgramData%\Everything 같은 공용 경로가 필요합니다. 주의: SQLite WAL 모드는 reader도 -shm/-wal 파일에 쓰기 접근이 필요합니다(read-only WAL은 제약이 많음). DB 디렉터리에 Users 그룹 modify 권한을 주되 DB 파일 삭제·교체는 막는 ACL 설계가 필요합니다.
  2. 변경 알림 채널: 현재 index_updated는 in-process Tauri 이벤트입니다. 서비스 → GUI 알림이 없으면 검색 결과 갱신을 알 수 없으므로, PRAGMA data_version 폴링(가장 단순) 또는 named pipe/event IPC가 필요합니다. 특히 GUI에서 rename/휴지통 실행 직후의 즉시 반영 — 지금은 GUI가 DB를 직접 쓰고 recent_ops 2초 캐시로 watcher 에코를 억제하는데 — 이 read-only에서는 서비스의 USN 반영(보통 <1초)을 기다리는 모델로 재설계해야 합니다.
  3. 제어 채널: reset_index, start_full_index, .pathignore/.pathindexing 변경 반영은 전부 쓰기 작업입니다. GUI/MCP가 서비스에 명령을 보내는 제어 IPC(named pipe RPC 등)가 필요합니다.
  4. 멀티유저 정보 노출: C:\ 전체 파일명이 담긴 DB를 모든 사용자가 읽으면 다른 사용자 홈 디렉터리의 파일명이 노출됩니다(Windows Search는 이를 per-user security trimming으로 처리). 단일 사용자 머신 전제면 무시 가능하지만, 배포 제품이라면 결과 필터링 또는 per-user DB 분리를 검토해야 합니다. 또 SYSTEM으로 도는 인덱서는 공격 표면이므로 최소 권한(Backup/Restore 권한만 가진 서비스 계정 등)도 고려 대상입니다.
  5. 이행 비용: GUI의 인덱서·watcher·finalize 경로 전체가 서비스로 이동하는 큰 리팩터링입니다. 서비스가 없거나 죽은 환경(설치 시 UAC 거부, 포터블 실행)에서도 앱이 동작해야 하므로 GUI writer 경로를 당장 제거할 수는 없습니다.

권장 순서

  1. daemon에 Windows 감시 경로(USN, 실패 시 RDCW)와 MFT 스캔을 배선 — 지금의 "60초 C:\ 전체 재스캔" 폴링부터 해소 (관리자 여부와 무관하게 가치 있음).
  2. DB를 공용 경로로 이전하고 data_version 폴링 기반 알림 + named pipe 제어 채널 설계.
  3. 서비스 등록을 installer의 opt-in(관리자 승인 시)으로 추가하고, GUI는 "writer lock을 서비스가 쥐고 있으면 reader 모드" 하이브리드로 전환.
  4. 하이브리드가 안정화되면 GUI writer 경로 축소를 검토.
