설계 v4: Windows 관리자 서비스 writer 전환

설치형 관리자 서비스가 index.db 쓰기를 전담하고, GUI·MCP는 read-only가 되는 구조 — Everything v0.5.1 코드 분석 기반 설계안 (2026-07-23) · Q1–Q4 확정 · v2: 1차 리뷰 25건(§9) · v3: 2차 리뷰 19건(§10) · v4: 3차 리뷰 — 신규 P1 4·P2 6 및 잔여 부분해결 반영(§11)

목표 (요구사항)
  1. Windows에서 설치 시점에 관리자 권한 서비스를 등록한다
  2. 서비스로 등록된 프로세스가 index.db 쓰기를 전담한다
  3. 인스톨러가 설치 시 관리자 권한(UAC)을 받아 서비스를 등록한다
  4. 인스톨러를 백그라운드(silent)로 실행해도 서비스가 자동 등록된다 — 승격 경로는 두 가지로 정의: (a) 이미 승격된 배포 채널(SCCM/Intune/관리자 콘솔)은 완전 무인, (b) 대화형 세션은 UAC 동의 1회. 비대화형·비승격 세션에서는 승격이 불가능하므로 실패가 정상 동작이며 종료 코드로 보고한다.
  5. GUI 프로세스와 --mcp 프로세스는 모두 DB read만 수행한다

1. 현행 구조 vs 목표 구조

현행(v0.5.x)은 "writer가 상황에 따라 바뀌는" 모델입니다: GUI가 떠 있으면 GUI가 writer, 없으면 비관리자 daemon이 writer. 그래서 gui.lock/daemon.lock 핸드셰이크, 인덱싱 패스 협조적 취소, GUI 감시 스레드 같은 writer 인계 장치가 필요했습니다 daemon.rs:36-61, 194-252 / main.rs:7170, 7235.

목표 구조는 "writer가 영원히 하나로 고정되는" 모델입니다. 설치 시 등록된 관리자 서비스가 유일한 writer이고, GUI·MCP는 언제나 reader입니다. writer 인계 자체가 사라지므로 핸드셰이크 계열 장치가 Windows에서 전부 불필요해지고, 관리자 권한이 상시 보장되므로 MFT 스캔 + USN 저널 체인을 항상 사용할 수 있습니다.

2. 핵심 설계 결정

D1. DB를 <ProgramData>\com.everything.app\로 이동하고, data/config를 ACL로 분리한다

이유: 서비스는 LocalSystem으로 실행되어 사용자별 %APPDATA%를 자연스럽게 가리킬 수 없고, 인덱스 대상 자체가 C:\ 전체(머신 전역)이므로 사용자마다 사본을 두는 것이 원래 낭비였습니다. 경로는 Rust에서 SHGetKnownFolderPath(FOLDERID_ProgramData)(또는 %ProgramData% 환경변수)로 해석 — C:\ProgramData 문자열 하드코딩 금지.

디렉터리 구조와 ACL (최소 권한):

  • data\ — index.db·-wal·-shm·usn.cursor·이관 마커·로그. Users: 읽기 전용(RX), SYSTEM/Administrators: Full. 일반 사용자의 DB·마커 훼손 벡터를 원천 제거.
  • config\ — .pathignore·.pathindexing 사이드카. Users: Modify — GUI(일반 권한)가 설정을 편집해야 하므로. 현행 코드는 사이드카를 DB와 같은 디렉터리에 두므로 main.rs:453-468 build_app_state가 config 경로를 별도 인자로 받도록 수정.

생성 주체와 선점(planting) 방지: 디렉터리 생성·소유권·ACL 설정은 인스톨러(승격 컨텍스트)가 서비스 시작 전에 수행합니다(§3.2 훅 0단계) — 기존에 같은 이름으로 선점된 디렉터리·junction이 있으면 소유권·ACL을 재설정. 서비스는 시작 시 handle 기반 검증을 추가로 수행: FILE_FLAG_OPEN_REPARSE_POINT로 열어 reparse point가 아님을 확인하고 owner가 SYSTEM/Administrators인지 검사 — 불일치 시 기동 거부 + 이벤트 로그(LocalSystem이 심긴 junction을 따라가 임의 위치에 쓰는 공격 차단).

config는 비신뢰 입력이자 제한된 채널:

  • .pathindexing root는 C:\ 볼륨 내로 제한 — canonicalize 후 볼륨 검증, 비-C·비존재·reparse 경유 경로는 무시 + 로그 + status 경고. LocalSystem이 임의 위치를 스캔하도록 유도하는 confused-deputy를 차단.
  • 절대경로 전용 규약: 머신 전역 config에서 ~/홈 상대 규칙은 거부 + 로그 — 현행 해석은 실행 계정의 home이라 main.rs:1187-1219 LocalSystem에서는 systemprofile이 되어 사용자 의도와 어긋나기 때문. 이관 시 GUI가 자기 홈 기준 절대경로로 정규화해 전송(§5).
  • 크기·항목 수 상한, 파싱 오류 무시. .pathignore로 인덱스를 사실상 비우는 가용성 공격은 R9 수용 리스크(변경 사실 로그 + 힐링).
  • 서비스와 Windows GUI는 기본 사이드카 파일을 생성하지 않습니다(파일 부재 = 내장 기본 규칙). 현행의 기본 템플릿 생성 main.rs:1305 / pathindexing.rs:26-31은 Windows에서 "편집 UI를 열 때 온디맨드 생성"으로 변경.

read-only WAL reader의 성립 조건 (정직한 서술): SQLite 3.22+는 -wal/-shm이 존재하고 읽을 수 있으면 read-only 연결로 WAL DB를 읽을 수 있습니다 — 상주 서비스가 RW 연결을 유지해 -shm을 살려두는 정상 상태에서 항상 성립합니다. 예외: 서비스 크래시 직후 등 -shm 복구가 필요한 순간에는 read-only 연결이 SQLITE_READONLY_RECOVERY/CANTINIT로 실패할 수 있습니다. reader(GUI/MCP)는 이 오류를 일시 상태로 처리: 백오프 재시도 + "인덱스 서비스 상태 확인" 배너(§D5). 복구 자체는 SCM이 서비스를 재시작하면 서비스의 RW 오픈이 수행합니다. Users에 디렉터리 Modify를 주는 방식은 채택하지 않습니다(불필요한 훼손 표면).

D2. 서비스는 everything --service — SCM 디스패처를 갖춘 진짜 Windows 서비스

SCM이 시작한 프로세스는 서비스 디스패처에 연결해 상태를 보고해야 하며, 일반 콘솔 프로세스를 그대로 등록할 수 없습니다. windows-service crate로 새 진입점을 새 파일에 만들고(win/service.rs), 인덱싱 코어는 기존 daemon의 빌드·힐링 루프를 재사용합니다.

상태 보고 규약 (정확한 SCM 의미론): 시작 즉시 START_PENDING 보고 → 빠른 준비만 수행(락 획득, 데이터 디렉터리 handle 검증(D1), 파이프 서버 오픈) → RUNNING 보고. RUNNING = "제어 가능한 상태"이지 "인덱스 준비 완료"가 아닙니다 — 인덱싱(수 분)은 RUNNING 이후 백그라운드로 수행하고, 인덱스 준비 여부는 파이프 status/meta로 별도 노출합니다. STOP 처리 중에는 STOP_PENDING을 checkpoint 증가와 함께 주기 갱신하며 진행 중 패스를 취소(§3.0 S7)합니다.

감시 체인은 GUI의 관리자 경로와 동일: USN resume → 실패 시 MFT 풀 스캔 win/mod.rs:66-95 미러링. RDCW·WalkDir 폴백은 서비스에서 제거하되, USN 자체가 기동 불가한 엣지(저널 생성 실패 등)에서는 서비스 내 주기 reconcile 재스캔(기존 daemon 폴링 모델 재사용)으로 강등 — 감시 공백을 남기지 않습니다.

서비스 객체 DACL — 서비스가 스스로 부여: 일반 사용자 GUI가 중지된 서비스를 UAC 없이 조회·시작할 수 있도록, 서비스가 첫 시작 시 자기 서비스 객체의 기존 DACL에 ACE를 추가합니다: GetNamedSecurityInfo/SetNamedSecurityInfo(SE_SERVICE)로 INTERACTIVE(S-1-5-4)에 SERVICE_START | SERVICE_QUERY_STATUS 부여 — 기존 DACL 보존, 멱등(이미 있으면 no-op). sc sdset은 DACL 전체를 교체해 위험하고 AU는 원격 인증 사용자까지 포함하므로 사용하지 않습니다. stop/삭제 권한은 부여하지 않습니다.

D3. GUI·MCP의 쓰기성 명령·상태 질의는 named pipe로 서비스에 위임한다 — 명시적 보안 모델 포함

서비스가 \\.\pipe\EverythingIndexer 파이프 서버(JSON 라인 프로토콜)를 엽니다.

  • 명령 집합: status(상태·진행률·카운트·버전·sidecarMigrated 플래그), reset_index(전체 재인덱스), migrate_sidecars(1회성 사이드카 이관 — §5, 마커로 멱등) — 끝. reindex_path는 confused-deputy 벡터라 제공하지 않습니다.
  • 파이프 보안: 생성 시 PIPE_REJECT_REMOTE_CLIENTS. DACL은 SYSTEM/Administrators Full + INTERACTIVE connect(read/write)만. 연결 수락 시 GetNamedPipeClientProcessId + 클라이언트 토큰 검사로 로컬 대화형 세션의 프로세스인지 확인.
  • slow-client 방어: 연결별 read/idle 타임아웃(예: 5초 — newline 미전송 연결은 끊음), 파이프 인스턴스 동시 N개(예: 4), 세션당 동시 1연결 — 연결 하나가 status/reset 채널을 봉쇄하지 못하게 함.
  • DoS 방어와 잔여 수용: reset_index는 쿨다운(전역 10분 1회) — 초과 요청은 거부 응답. 잘못된 JSON·과대 페이로드(줄 길이 상한)는 즉시 연결 종료, 요청은 순차 처리. 잔여("어떤 로컬 사용자든 10분마다 전역 reset 가능")는 R9 수용 리스크.
  • 감사의 정확한 범위: 파이프 명령(reset·migrate)은 호출 PID·세션을 기록합니다. config 파일 직접 편집은 변경 사실·시각만 기록 가능 — USN은 작성 프로세스를 제공하지 않으므로 usn_watcher.rs:256-264 행위자 식별을 주장하지 않습니다(R9).
  • 실행 의미론: 파이프 스레드는 요청을 검증·기록 후 인덱서 큐에 enqueue만 하고 즉시 접수 응답 — 실행·경합 규칙은 §3.1의 단일 인덱서 큐가 담당.

D4. 상태·진행률은 파이프 일원화, data_version은 Ready 상태에서만 사용한다

서비스는 Tauri AppHandle이 없어 index_progress/index_state/index_updated 이벤트를 emit할 수 없습니다. 대체 설계:

  • 진행률/상태 = 파이프 status: GUI가 인덱싱 중 500ms~1s 폴링 → 백엔드가 기존 이벤트 이름(index_state/index_progress)으로 재-emit → 프런트엔드(App.svelte) 무변경. 진행률을 meta 테이블에 고빈도 커밋하지 않습니다(data_version 자기 교란 방지). meta에는 전이 시점의 최종 상태(svc_state=Ready/Error)만 기록(파이프 부재 시 폴백·MCP 안내용).
  • index_updated 대체 = PRAGMA data_version: Ready 상태에서만 전용 장기 read 커넥션으로 1–2s 주기 확인(data_version은 연결별 값이므로 전용 커넥션 필수). 값이 바뀌면 현재 검색 재실행. 인덱싱 중에는 status 폴링이 주기 갱신을 겸하므로 data_version 폴링은 끕니다. 유휴 시 무시-이벤트 cursor 저장은 DB 밖(파일)으로 분리(§3.0 S4)되어 data_version을 건드리지 않습니다.
  • 서비스 생존 판정은 meta가 아니라 SCM: 서비스가 죽어도 meta에는 마지막 svc_state=Ready가 남으므로, GUI의 헬스 판단은 SCM 상태 질의(QueryServiceStatus) + 파이프 연결성 + 버전 대조로 하고 meta는 보조로만 씁니다(§D5).

D5. 서비스 등록은 인스톨러가 전담. 앱은 SCM 기준으로 헬스를 판단하고, 자가 복구는 검증된 설치 바이너리만 등록한다

GUI는 시작 시·주기적으로 SCM을 질의해 상태를 구분 처리합니다:

  • 미설치 → "인덱스 서비스가 없습니다 — 등록" 배너. 등록 버튼은 ShellExecute(runas)로 everything --register-service 실행(UAC). 이 복구 명령은 최초 릴리스(Phase 3)에 포함 — 설치 실패 잔여 상태(§3.2 실패 의미론)의 복구 경로가 릴리스 시점부터 존재해야 하므로.
  • 설치됨·중지 → D2에서 부여한 SERVICE_START 권한으로 UAC 없이 자동 시작 시도 → 실패 시 안내 배너.
  • 실행 중·파이프 무응답 / 버전 불일치(status 응답의 버전 ≠ GUI 버전) → 오류 배너 + 재시작 유도. crash-loop은 SCM 복구 정책(§3.2)이 감독.

권한 상승 방지 (필수 불변식): --register-service는 자기 자신의 경로를 그대로 등록하지 않습니다. 등록 대상 exe는 관리자만 쓰기 가능한 설치 디렉터리(Program Files 설치본, 레지스트리 설치 정보로 확인)의 바이너리로 한정하고, 경로 ACL을 검증해 사용자 쓰기 가능 위치(portable/dev 실행본)면 등록을 거부하고 인스톨러 설치를 안내합니다. 같은 원칙이 마이그레이션에도 적용됩니다: 승격 컨텍스트에서 사용자 쓰기 가능 위치의 실행 파일(구 per-user 언인스톨러 포함)을 실행하지 않습니다(§5). dev 환경은 문서화된 수동 절차로만 등록합니다.

서비스 부재 시 GUI가 writer로 되돌아가는 폴백은 두지 않습니다(요구사항 ⑤ 위반이며 dual-mode 복잡성의 근원). read-only GUI는 기존 DB로 검색은 계속 동작합니다.

D6. Windows에서 writer 핸드셰이크 계열 장치를 제거한다

구조적으로 writer가 하나뿐이므로 다음이 Windows에서 불필요해집니다: GUI beacon main.rs:7170, wait_for_daemon_exit main.rs:7235, build_index의 GUI 감시·취소 스레드 daemon.rs:200-224, run_windows_resident의 yield 루프 daemon.rs:442-488, MCP의 daemon spawn mcp_server.rs:452. 단 daemon.lock은 서비스가 계속 보유합니다 — 실수로 띄운 --daemon이 자진 종료하는 안전망(기존 로직 그대로). macOS 경로는 전부 유지됩니다. 제거는 반드시 §7의 릴리스 규칙(Phase 0–3 일괄 배포)과 함께 — 부분 배포 시 dual-writer가 부활합니다.

4. 동작 시나리오

  1. 최초 설치: 인스톨러 실행 → UAC 승격 → 파일 복사 → 훅: 데이터 루트 생성+ACL → 서비스 등록 → 복구 정책 → 시작 + RUNNING 확인 → (성공 후) 구 per-user 설치 파일 정리 → 서비스가 즉시 MFT 풀 스캔. 사용자가 나중에 GUI를 열면 검색 즉시 동작, 설치 직후 수 분 내에 열면 진행바(파이프 status). 등록/시작 실패 시: 구 설치 보존 + 새 GUI 배너의 --register-service(동일 릴리스 포함)로 복구.
  2. 부팅: delayed-auto로 서비스 시작 → USN resume. GUI가 서비스보다 먼저 뜨면: read-only라 기존 DB로 즉시 검색 가능(직전 세션까지 반영), 서비스가 뒤이어 올라오며 오프라인 변경분을 수 초 내 흡수. 중지 상태로 판정되면 부여된 SERVICE_START 권한으로 직접 시작 시도(D5).
  3. 일상 사용: 파일 생성/삭제/rename → USN 이벤트 → 서비스가 upsert/delete, 디렉터리 rename은 old·new 양쪽 subtree rescan(S6)으로 하위 경로까지 정정 → GUI는 data_version 변화 감지 시 현재 검색 재실행(~1–2초 반영).
  4. GUI에서 재인덱스: 파이프로 reset_index 전송(쿨다운 10분, 감사 로그) → 인덱서 큐 enqueue → 워커가 watcher 정지 장벽 후 실행, GUI가 status 폴링으로 진행바 표시.
  5. 업데이트(백그라운드): 새 인스톨러를 /S로 실행 → 승격(§3.2의 세 경로) → 훅: 서비스 정지 확인(폴링, 진행 중 스캔은 S7 취소로 수 초 내 중단) → 파일 교체 → 서비스 재시작 + RUNNING 확인 → USN resume으로 정지 구간 흡수.
  6. 서비스 이상: 미설치 → 등록 배너(검증된 설치 바이너리만, D5) / 중지 → 무권한 자동 시작 시도 / 무응답·버전 불일치 → 안내 배너. 크래시는 SCM 복구 정책이 재시작, 재시작 후 힐링이 미완성 빌드를 복구.
  7. 언인스톨: 훅이 서비스 정지(폴링)+삭제(완료 확인) → 파일 제거 → data\(인덱스·로그)만 삭제, config\(사용자 규칙) 보존 — 열린 핸들로 실패 시 /REBOOTOK로 재부팅 시 삭제 예약 (Q1 범위 명확화).

6. 리스크 / 트레이드오프

R1 관리자 인덱스의 정보 노출 — 정확한 범위 (수용 리스크)

LocalSystem 서비스는 ACL로 보호된 경로(다른 사용자 프로필 포함)까지 인덱싱하며, DB에는 파일명만이 아니라 전체 경로·사용자명·디렉터리 구조·크기·mtime이 들어가고 mft_indexer.rs:583 이것이 모든 로컬 사용자에게 읽힙니다(내용은 제외). 이는 접근통제가 아니라 명시적으로 수용한 리스크입니다(Q2 확정): 지배적 사용 사례가 단일 사용자 데스크톱이고, 원조 Everything의 서비스 모델과 동일한 트레이드오프. 다중 사용자 머신 관리자를 위해 스펙·설치 문서에 이 특성을 명시하고, C:\Users\<타 사용자> 제외 옵션을 후속 릴리스 과제로 등록합니다.

R2 DB 훼손 표면 — v2에서 대폭 축소

data\가 읽기 전용으로 잠겨(D1) 일반 사용자의 DB·WAL·이관 마커 훼손 벡터가 제거됐습니다. 남는 표면은 config\ 사이드카(Users Modify)뿐이며, 서비스는 이를 비신뢰 입력으로 파싱(크기·항목 상한, C:\ 볼륨 제한, 절대경로 전용, 잘못된 규칙 무시)합니다. 관리자 권한 사용자의 훼손은 힐링 루프 + 오픈 실패 시 재생성으로 복구.

R3 이벤트 → 폴링 전환에 따른 반영 지연

watcher가 GUI 프로세스 밖으로 나가므로 index_updated 즉시 emit이 사라지고 data_version 폴링(Ready 상태, 1–2s)으로 대체됩니다. rename 직후 재검색에 이전 이름이 잠깐 보일 수 있음. 완화: 낙관적 표시 갱신 + 파일 조작 직후 폴링 주기 일시 단축. 인덱싱 중 상태는 파이프 status가 담당하고 유휴 cursor는 DB 밖 파일에 저장(S4)되므로 폴링 자기 교란이 없습니다.

R4 UAC 필수화 — 설치 장벽

per-user 설치(무권한)가 사라지므로 관리자 권한이 없는 사용자는 설치 불가. 요구사항 ①·③의 의도된 트레이드오프 — 관리자 권한을 "설치 시 1회"로 집중시키는 대가로 상시 MFT/USN·GUI 무권한 실행을 얻습니다.

R5 GUI 첫 실행 즉시검색(MemIndex) 소멸

MemIndex는 GUI-스캔 모델의 보완 장치였고, 서비스 모델에서는 설치 직후 서비스가 선-인덱싱하므로 필요 자체가 사라집니다. "설치 직후 수 분 내 GUI를 연" 경우에만 진행바를 보게 됨 — 현행과 동일한 체감.

R6 코드 복잡도

새로 드는 것: 서비스 디스패처·인덱서 큐·파이프 서버(보안 검사 포함)·NSIS 훅·Phase 0 견고화. 사라지는 것: Windows writer 인계 핸드셰이크 전부, GUI 4단 폴백 체인 기동, MemIndex(win), recent-ops 캐시(win), MCP daemon spawn(win). 신규 작업의 상당 부분은 현행 코드에도 존재하던 결함의 수정(Phase 0)이며, dual-writer 버그 클래스 소멸이라는 이득은 그대로입니다.

R7 볼륨 가정

인덱싱 범위는 현행과 동일한 C:\ 단일 볼륨이며, 시스템 볼륨은 NTFS(Windows 요구사항)라 MFT/USN이 성립합니다. USN 저널이 비활성/삭제된 엣지에서는 서비스가 저널을 생성(FSCTL_CREATE_USN_JOURNAL, 관리자라 가능)하고, 그래도 기동 불가하면 주기 reconcile 폴백으로 강등(D2) — 감시 공백은 없되 반영 지연이 커집니다. .pathindexing의 비-C root는 v1 범위에서 거부(무시+경고, D1). 다중 볼륨·mount point·ReFS 지원은 명시적 비범위(후속 과제).

R8 단일 바이너리 유지 (전용 서비스 exe 채택 보류)

인덱싱 코어를 lib으로 분리해 작은 전용 서비스 exe를 두는 안(공격면·수명주기 단순화)은 타당하나, 현재 코어가 바이너리 크레이트의 main.rs(~4,800줄)에 있어 lib 추출이 대규모 리팩터링입니다. --service 경로는 CLI 분기가 Tauri 초기화 전에 일어나므로 main.rs:7538-7543 패턴 Tauri/WebView 런타임을 초기화하지 않으며, 단일 바이너리를 유지하고 lib 분리는 후속 리팩터링 과제로 등록합니다. (리뷰 재확인: 바이너리 결합 자체는 남는다는 점을 인지한 의도적 보류 — 3차 리뷰에서 타당 판정.)

R9 로컬 사용자에 의한 인덱스 가용성 공격(DoS) — 수용 리스크 + 신뢰 모델 선언

스펙 선언: 본 제품은 로컬 사용자 간 보안 경계를 제공하지 않습니다(single trust domain — R1의 전역 메타데이터 노출과 동일한 모델, 원조 Everything과 동일). 로컬 사용자 간 보안 경계가 필요한 환경(공용 PC·멀티테넌트)은 v1 지원 대상이 아니며 설치 문서에 명시합니다. 이 선언 하에서: 어떤 로컬 대화형 사용자든 (a) 파이프 reset_index를 쿨다운 한도(전역 10분 1회) 내에서 반복하거나 (b) config\.pathignore를 광범위 규칙으로 채워 전역 인덱스를 사실상 비울 수 있습니다 — 기밀성 침해가 아닌 가용성 문제로, 수용합니다. 감사의 한계를 정확히: 파이프 명령은 호출 PID·세션이 기록되지만, config 파일 직접 편집은 변경 사실·시각만 기록됩니다(USN은 작성자를 제공하지 않음 — D3). 힐링·reconcile이 정상 설정 복원 시 자동 복구하며, config를 Administrators-write로 잠그는 설치 스위치는 후속 옵션 과제(설정 편집 UX 훼손 때문에 v1 기본이 아님).
